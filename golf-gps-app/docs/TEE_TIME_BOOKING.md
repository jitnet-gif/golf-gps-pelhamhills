# 티타임 예약 (`/book`)

GPS 웹앱에서 손님이 직접 티타임을 잡습니다. 홈 화면의 **Book a tee time** 카드로
들어갑니다.

프로 샵 화면(웹사이트의 `/teesheet`)과 **같은 티 시트 데이터**를 봅니다. 앱에서
잡은 예약은 직원 격자에 즉시 나타나고, 직원이 막아 둔 시간은 앱에서 사라집니다.

```
GPS 앱 /book ──> FastAPI /api/v1/tee-sheet/*  <── 웹사이트 /teesheet (직원)
                        │                     <── 웹사이트 /book/tee-time (손님)
                        └─ backend/services/tee_sheet_store.py (JSON + RLock)
```

`VITE_API_URL`이 가리키는 Cloudflare Worker와는 **다른 백엔드**입니다. Worker는
스코어·푸시·배너를 맡고, 예약은 이 FastAPI만 맡습니다. 예약 화면은 Worker를
전혀 거치지 않습니다.

---

## 1. 설정

### 1-1. 앱 쪽

`frontend/.env.local`(또는 배포 환경변수)에 예약 서버 주소를 넣습니다.
**버전 접두사(`/api/v1`)까지** 포함해야 합니다.

```bash
VITE_TEE_SHEET_API_URL=https://api.example.com/api/v1
```

비워 두면 로컬 개발에서는 `http://localhost:8000/api/v1`로 붙습니다. 배포된
사이트에서는 loopback 주소를 쓸 수 없는 것으로 취급해서 예약 화면이 폼 대신
**프로 샵 전화번호**를 보여줍니다. 개발 기본값이 번들에 박힌 채 배포되어
방문자의 브라우저가 자기 컴퓨터의 8000 포트를 두드리는 사고를 막기 위해서입니다
(판정은 `frontend/src/lib/teeSheet.ts`의 `teeSheetBaseUrl()`).

### 1-2. 백엔드 쪽 (CORS)

앱과 예약 서버는 출처가 다릅니다. FastAPI의 `ALLOWED_ORIGINS`에 앱 주소가 없으면
브라우저가 요청을 막고, 화면에는 "예약 서버에 닿지 못했다"만 남습니다 —
서버 로그에는 아무것도 찍히지 않으므로 네트워크 문제로 오해하기 쉽습니다.

개발용 `http://localhost:5173`(Vite dev)과 `http://localhost:4173`(vite preview)는
`backend/core/config.py`의 기본값에 들어 있습니다. **배포 주소는 직접 넣어야
합니다.**

```bash
ALLOWED_ORIGINS=http://localhost:3000,http://localhost:5173,https://gps.example.com
```

## 2. 화면

날짜 → 인원 → 시간 → 이름, 네 걸음입니다.

| 단계 | 하는 일 |
| ---- | ------- |
| 날짜 | 오늘부터 14일. 그 너머는 프로 샵이 요금·행사를 확정하지 않은 구간입니다. |
| 인원 | 1~4명. 한 티타임은 4자리이고, 여러 예약이 나눠 가질 수 있습니다. |
| 시간 | 9분 격자 중 **자리가 남은** 시각. 인원이 안 되는 시간은 지우지 않고 눌러 둡니다. |
| 이름 | 이름·이메일(필수), 전화(선택), 홀 수, 카트. 결제는 체크인 때 프로 샵에서. |

## 3. 남은 자리를 어떻게 세는가

백엔드에는 "손님이 살 수 있는 티타임" 엔드포인트가 없습니다. 있는 것은 그날의
격자(`/tee-sheet/slots`)와 그날의 예약 전부(`/tee-sheet/bookings?date=`)뿐이라,
둘을 겹쳐서 `frontend/src/lib/availability.ts`가 계산합니다.

서버의 `tee_time_players()`와 **같은 규칙**을 씁니다.

- 취소된 예약은 자리를 잡지 않는다.
- 만료된 음성 홀드는 서버가 목록 응답에서 이미 빼고 준다.

여기에 더해 두 가지를 손님에게서 숨깁니다. 둘 다 서버는 막지 않으므로, 화면에서
막지 않으면 손님이 못 쓸 시간을 사게 됩니다.

- `blocked` 예약이 걸린 티타임 (대회·정비. 플레이어가 0명이라 자리 계산으로는
  4자리가 다 비어 보이고 POST 도 성공합니다).
- 이미 지나간 시각 (서버에 "과거 티타임 예약 금지" 규칙이 없습니다).

> 이 규칙은 웹사이트 쪽 `frontend/components/booking/availability.ts`와 같은
> 내용입니다. 두 앱은 빌드가 갈라져 있어(Next / Vite) 모듈을 공유할 수 없으므로
> **한쪽을 고치면 다른 쪽도 고쳐야** 합니다.

## 4. 예약을 만들 때 지켜야 하는 두 가지

`frontend/src/pages/Book.tsx`의 POST 본문에 주석으로도 달아 두었습니다.

1. **인원 = `players` 배열의 길이.** 서버의 정원 검사가 `incoming=len(body.players)`
   라서, 3인 예약을 플레이어 객체 하나로 보내면 자리는 1개만 잡히고 같은
   티타임이 다시 팔립니다.
2. **`rate`를 보내지 않는다.** 서버가 그날의 슬롯 요금을 매깁니다. 화면에 굳어
   있던 값을 보내면 프로 샵이 요금을 바꾼 날 손님이 옛 가격으로 예약합니다.

## 5. 실패는 언제나 전화번호로 착지한다

코스에서 열리는 앱이라 신호가 없을 수 있습니다. `describeFailure()`가 세 갈래로
나눕니다.

| 상황 | 화면 |
| ---- | ---- |
| 서버에 못 닿음 (status 0) | "다시 시도" + 프로 샵 전화번호. 서버 주소는 절대 노출하지 않습니다. |
| 409 (고르는 사이 자리가 나감) | 오류 배너가 아니라 **시간 목록으로 되돌리고** 새로 불러옵니다. |
| 그 외 (422 등) | 서버가 준 `detail` 문장을 그대로 보여줍니다. |

## 6. 서비스 워커는 예약 API를 캐시하지 않는다

`vite.config.ts`의 일반 `/api/` 규칙은 NetworkFirst(5분 캐시)입니다. 여기에
예약 API가 잡히면 남은 자리 수를 최대 5분 묵은 값으로 보여주고, 손님은 이미 찬
시간을 눌러 409를 맞습니다. 그래서 `tee-sheet` 경로만 **NetworkOnly**로 앞에
두었습니다 — 규칙 순서가 곧 우선순위입니다.

오래된 답을 주느니 실패하는 편이 낫습니다. 실패는 위 표대로 전화번호로 착지합니다.

## 7. 아직 없는 것

- **예약 조회·취소.** 웹사이트에는 `/book/lookup`이 있지만 앱에는 없습니다.
  확인 화면과 이 문서 모두 변경·취소는 전화로 안내합니다.
- **예약 출처 구분.** 서버의 `CreateBookingRequest`에 `source` 필드가 없어서
  앱에서 만든 예약도 티 시트에 `staff`로 기록됩니다(웹사이트의 `/book/tee-time`도
  같습니다). 지금은 `notes`의 "Booked from the Golf GPS app." 문구로만 구분됩니다.
